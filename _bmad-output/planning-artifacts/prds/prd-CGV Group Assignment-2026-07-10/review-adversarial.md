# Adversarial Review — SAMS PRD

Reviewed: `prd.md` (2026-07-10) against `CS402.3 Coursework.md` and the five actual sample photos in `sample_signin-sheets/` (1.jpeg–5.jpeg, inspected directly).

## Verdict

This PRD reads like it was written from the brief's idealized table, not from the five real photos: the samples show signatures straddling row boundaries, overlapping each other, spilling outside the table border, and marker/grader annotations crossing into the table — all of which break the PRD's "ink in cell = Present" model that carries the graded 60%. Meanwhile the two artifacts everything else depends on — the `info.xml` schema and the sheet identifier — are left as open questions, so a 10-person team cannot parallelize on day one, and the Web UI adds three FRs of ungraded work on top. Buildable eventually, but the hard 20% of the problem is exactly where the PRD is vaguest.

## Findings

### Critical

- **Sheet identifier has no defined source — FR-6/FR-7/FR-8 are keyed on a value nobody can produce** (§3 Glossary "Metadata Row", FR-6, §9 idempotency assumption) — The Attendance Record and the idempotency key are `(Student Index, sheet identifier)`, and the Glossary says "the Date is a useful source for the Sheet identifier." But on the real sheets the date is *handwritten* (`31/05/2019`, `28.6.2019`, `12.07.2019` — three different formats), and handwriting-to-text OCR is an explicit Non-Goal (§5). The brief's example filename (`10.07.2019.png`) encodes a date, but the actual samples are named `1.jpeg`–`5.jpeg`, so filename-derived dates fail too, and the undefined `info.xml` (OQ-1) may or may not carry a session date. Result: FR-6 persistence, FR-6 idempotency, FR-7 "all Attendance Records," and FR-8's per-session graph all hang off a field with no obtainable value. — Fix: decide now — e.g. identifier = image filename (documented convention), or a required `<session date=...>` element in `info.xml`, or an explicit CLI/UI-supplied date; then restate FR-6's key.

- **Signature bleed-over invalidates the per-cell detection model — and FR-2 makes it worse** (FR-2, FR-3, FR-4, §4.1 NFR) — Visible in the actual samples: on 1.jpeg signatures sit on the boundary between rows (one signature serves as ink for two cells), one student's signature is partly *outside* the table border in the right margin, and row 6's signature extends below the table; on 5.jpeg two signatures overlap across rows 1–2 and a thick black marker stroke crosses into the table's top-left corner. FR-4's rule "cell contains handwritten ink → Present" will double-count straddling ink, assign it to the wrong row, or miss it. Worse, FR-2's testable consequence — "handwritten margin annotations outside the table are excluded before analysis" — would *delete the evidence of a real signature* (the margin-spilling one on 1.jpeg) and flip a Present to Absent. No FR says how ink spanning two cells is attributed. This is the graded core; SM-1 targets 100% on exactly these five sheets. — Fix: add an FR defining ink-attribution policy (e.g. assign connected components to the cell containing their centroid/majority area; dilate cell ROIs; treat table-adjacent margin ink as candidate signature, not annotation) and rewrite FR-2's margin-exclusion consequence to exclude only ink far from the table.

- **`info.xml` schema undefined — the single most load-bearing contract is an open question** (OQ-1; blocks FR-1, FR-5, FR-6, FR-7, FR-9, FR-10, FR-12, FR-15) — FR-1 must "parse the Info File into Student Records," FR-5 maps rows to indices, FR-6 stores its "subject/session metadata," FR-7/FR-10 take its index as the CLI argument, and §3 declares it "the source of truth for valid indices" — yet its element structure is deferred to OQ-1, and the brief's "Figure 1" was never supplied. Until someone invents this file, the DB schema, parser, CLI contract, mapping logic, and Web UI upload validation are all blocked: a 10-person team cannot split the work. Also note the brief says "a text file"; the PRD confirmed XML — fine, but that means the *group* must author the file, so there is no excuse for not defining it in the PRD. — Fix: put a concrete sample `info.xml` (students with 8-digit index, name, title, `No` ordinal; subject; session date) in an appendix and mark it the normative schema pending module-leader override.

### High

- **Reference Signatures are circular — `investigate.py` may verify a signature against itself** (FR-9, FR-10, OQ-2, SM-4) — The only signature source in the project is the five sample sheets, which are also the sheets being investigated. If references are cropped from those sheets, a "match" is near-tautological and a grader will see through it; if hand-collected, that's an unplanned data-collection task for six real people (the sheets name actual students the team cannot contact). Per student there are at most 5 samples (fewer — some are absent on some sheets), several contaminated by bleed-over from adjacent cells. And FR-10's assumed method (ORB/SIFT-style feature matching) is notoriously weak on tiny low-texture scribbles. The PRD itself calls this "the riskiest technically" and then resolves nothing. SM-4's "deliberately mismatched signature" test set does not exist yet. — Fix: mandate the protocol in the PRD — e.g. references = crops from sheets {1,2,3}, probes = crops from sheets {4,5}, mismatch set = other students' signatures; require a documented similarity metric with a threshold justified on that split.

- **Student Index mismatch is "resolved" by deferring to a file that doesn't exist** (§3 Glossary "Student Index", OQ-4, UJ-4, FR-7) — The Glossary's answer to the 8-digit-vs-`001` clash is "the Info File is the source of truth" — but the Info File is undefined (OQ-1), so this is a pointer into the void. Concrete failure: a grader runs the brief verbatim — `python infovis.py 001` — against a DB keyed on `10009301`; FR-7's specified behavior is to report "no data." The program looks broken during marking precisely because it followed the PRD. — Fix: require both forms to resolve — treat `001` as the sheet's `No` ordinal / a short alias mapped in `info.xml`, and accept the 8-digit Student No; document the mapping in `--help` output.

- **FR-11 vs FR-13 / Streamlit execution-model conflict is unaddressed** (FR-11, FR-13, §4.6 assumption, FR-15) — FR-11 permits "window display" (i.e. `cv2.imshow`) for the CLI; that call cannot run inside a Streamlit server thread, and Streamlit's rerun-the-whole-script model makes "watch stages render live" (UJ-1) non-trivial — a naive port reprocesses the sheet (and rewrites the DB) on every widget interaction, which collides with FR-6 idempotency, whose key is itself undefined (see Critical #1). FR-13 "mirrors FR-11" guarantees two display code paths over the same stages; without an explicit engine-emits-stage-artifacts contract, they will drift and violate FR-15's "no duplicated logic." — Fix: specify that the Core Engine yields labelled stage images via a callback/generator and both frontends only render; forbid `cv2.imshow` inside the engine; require processing to be an explicit one-shot action in the UI.

- **The Web UI adds ~3 FRs of work that earns zero rubric marks** (§4.6, FR-12–FR-14, SM-6 vs §7's own framing) — The assessment table grades: program quality/OOP, executable program, image-processing libraries and techniques (60%), plus report and contribution. Nothing awards marks for a responsive mobile browser UI, touch targets, or upload flows. §7 claims metrics are "anchored to the coursework assessment criteria," then includes SM-6 (phone usability) which maps to no criterion. For a student team the realistic outcome is the strongest members polishing Streamlit while cell localization — the graded hard part — stays brittle. The Web UI also drags in the fresh-machine risk below. — Fix: keep it, but the PRD must sequence it: Web UI work starts only after SM-1–SM-4 pass on all five sheets, and cap it (one page, no custom CSS). State explicitly that it is a demo aid, not a grade lever.

- **SM-1's ground truth is assumed, but the samples make ground truth itself ambiguous** (SM-1, §9 final assumption, OQ-5) — §9 assumes "who actually signed each of the five sample sheets is known/derivable." On 1.jpeg and 5.jpeg, signatures float between rows and overlap; deciding *which student* a boundary-straddling signature belongs to requires human adjudication, and reasonable people will disagree. Without a frozen answer key, "100% accuracy" is unmeasurable and the escape hatch "or every error explainable" makes SM-1 unfalsifiable — a grader-proof-sounding metric that can never fail. — Fix: require a committed `ground_truth.csv` (sheet × student → Present/Absent/Disputed), adjudicated by the team *before* tuning, and redefine SM-1 against it with Disputed rows scored separately.

### Medium

- **"Fresh setup" (SM-2) has no supporting requirement — the graded commands can die on import** (SM-2, FR-15, §4.7) — No FR requires a `requirements.txt`/`pyproject`, a stated Python version, or dependency isolation. If the Core Engine package (which the CLI imports per FR-15) transitively imports Streamlit, a marker running exactly `python sams.py 10.07.2019.png info.xml` on a machine without the web stack gets `ModuleNotFoundError` — instant "executable program" mark loss. Also: the brief's example is `.png`, the real samples are `.jpeg`; trivial, but must be tested, and no FR names supported formats. — Fix: add an FR: engine and CLI depend only on OpenCV/NumPy/Matplotlib/stdlib-sqlite3; web dependencies live in an optional extra; pinned requirements file; smoke-test on a clean venv.

- **Two stacked look-alike tables + printed-template ink: localization stages are hand-waved** (FR-3, FR-4) — Every sheet has *two* grids of near-identical width (the Date/Lecturer metadata table directly above the student table), so "detect the table grid" via largest-contour or line detection can grab the wrong table or merge both; FR-3 just asserts the metadata row is skipped without any mechanism (row count? vertical position? column count 4 vs 5?). Within cells, FR-4 must separate pen ink from printed borders bleeding into the ROI under perspective distortion, plus white-out patches (1.jpeg) and a red grader "④" annotation (3.jpeg) that pen-colour tolerance can't filter by hue. None of these appear as pipeline stages in FR-2/FR-11 (no border-removal/template-masking stage is named). — Fix: name the mechanism (e.g. select the grid with 5 columns and ≥2 rows below the header band; mask detected grid lines before ink measurement) so it's testable rather than aspirational.

- **UJ-1/FR-13 promise a "flagged/ambiguous" state the data model cannot represent** (UJ-1, FR-13, OQ-5, §3 "Attendance Record") — The journey promises ambiguous cells are "flagged for her review rather than silently guessed," and FR-13 requires flagged rows to be "visually distinguished" — but the Attendance Record is defined as binary `Present|Absent`, no FR defines the ambiguity criterion or the review/override action, and OQ-5 admits the policy is undecided. The UI is specced to display a state that cannot be stored, and there is no FR for what Nadeesha *does* with a flagged row. — Fix: either add a third stored state + a manual-override FR, or delete the flagging promise from UJ-1/FR-13 and force a decision (and say so).

- **FR-14's "identical in content" parity consequence is untestable as written** (FR-14, FR-15) — "The attendance graph … renders in the browser identical in content to the `infovis.py` output" compares a Matplotlib window to a browser render; "identical in content" has no defined check. FR-15's DB-level parity consequence is testable; FR-14's is vibes. — Fix: define parity at the data layer (same figure object / same underlying query results), not the pixels.

- **Visualization — one of the brief's two "key technologies" — is left as "chart TBD"** (FR-8, OQ-3, §9) — The brief names data visualization as a co-equal graded focus, and `infovis.py` is a whole deliverable program; the PRD offers "counts and/or trend, exact chart TBD." That's not enough for anyone to build or for a grader-facing "suitable graph … applying data-visualization technique" claim. — Fix: commit a default (e.g. per-session presence timeline + attendance-rate summary, labelled) and let OQ-3 upgrade it, not define it.

### Low

- **Row-count generality vs "static known layout" tension** (§4.1, §6.2, SM-C1) — All five samples have exactly 6 student rows, but the brief's prototype must accept "different images"; §6.2 scopes to "the single static known layout" while SM-C1 forbids overfitting. Say explicitly: column layout fixed, row count dynamic.

- **Template typos forbid header-text reliance** (FR-3) — The printed headers read "Lecture's Name" and "Signatue" (sic). Any teammate tempted to OCR-match header labels for localization should be warned off; nothing in the PRD prevents that dead end.

- **Date-format normalization** (§3 Metadata Row) — Even if a human types the sheet date, three formats appear across five sheets (`31/05/2019`, `28.6.2019`, `12.07.2019`). Whatever fixes Critical #1 must define one canonical format for the DB key.

- **Working title still unconfirmed** (§0/§1 "*Working title — confirm*") — Cosmetic, but a draft-status header plus unconfirmed title in a document 10 people build from invites "which version is current?" churn. Resolve before circulation.

Poor (pre-fix)

The rubric review finds a genuinely usable coursework PRD: it has a real thesis (grade-anchored, one Core Engine behind two frontends), FRs with genuinely testable consequences, and unusually honest scope machinery (Non-Goals, tagged assumptions, open questions that are actually open). Two things are at risk on the rubric alone: the committed higher-grade component (investigate.py) rests on a reference-signature capture pathway the PRD never defines, and ambiguous-cell handling is half-decided — asserted in UJ-1 and FR-13 while simultaneously listed as Open Question 5.

The adversarial reviewer, who inspected the five actual sample photos, materially shifts the picture — and drives the pre-fix grade to Poor under the "any critical finding" rule. Three criticals: (1) the sheet identifier that keys FR-6/FR-7/FR-8 has no obtainable source (dates are handwritten, OCR is a Non-Goal, real files are named 1.jpeg); (2) real signatures straddle row boundaries and spill outside the table, breaking the "ink in cell = Present" model and making FR-2's margin-exclusion rule actively harmful; (3) the info.xml schema — the single most load-bearing contract — is deferred to an open question, blocking eight FRs and preventing a 10-person team from parallelizing. The brief-coverage audit confirms nothing from the brief is missing (26 covered / 4 partial / 0 missing) but flags the Web UI as the largest un-briefed effort-diversion risk. All critical and high findings were fixed in the PRD immediately after this review ran — see the memlog for the fix trail.

Decision-readiness

adequate

The PRD makes real decisions and says so: investigate.py is "committed for this build" with the risk named in the same breath; the Web UI framework is recommended, not smuggled in as settled; SM-C1 names an honest trade-off. Two things keep it from strong: the largest scope decision in the document — adding a mobile Web UI on top of a brief that specifies only three CLI programs — is asserted in the Vision without its cost being weighed; and OQ-5 asks how ambiguous cells should be handled while UJ-1 already answers it. The decision is half-made in three places.

medium

Web UI scope decision lacks a stated trade-off

§1 Vision, §4.6
The PRD's biggest scope addition beyond the brief is presented as settled with no acknowledgment of what it costs against the graded criteria.
Fix: Add one honest paragraph naming the bet: Web UI effort buys SM-6 and demo polish, at the cost of engine-hardening time; state the fallback if the group runs short.
medium

Ambiguous-cell handling both decided and open

UJ-1, FR-13 vs OQ-5
UJ-1 says ambiguous rows are "flagged for her review rather than silently guessed" and FR-13 requires flagged rows "visually distinguished," yet OQ-5 asks whether to flag or force a decision.
Fix: Either commit to flagging (make it an FR consequence with a defined ambiguity criterion and delete OQ-5) or strip the flagging behaviour from UJ-1/FR-13.

strong

The two personas each earn their place; the NFRs are conspicuously product-specific ("desk background, punch holes, and handwritten margin notes" could only have been written by someone who looked at the actual sample sheets); the Vision names the pipeline stages and the three concrete programs; SM-C1 is an earned counter-metric. No findings.

Success Metrics are anchored to the assessment criteria rather than generic activity metrics, each SM names the FRs it validates, and a counter-metric exists.

Done-ness clarity

adequate

The soft spots cluster exactly where the grade risk is highest: FR-9 has no mechanism anywhere in the document by which a reference signature enters the system; FR-8 leans on "a suitable graph" — adjectives where a decision should be; and "genuinely ambiguous" cells have no criterion.

FR-8, OQ-3

medium

No ambiguity criterion

FR-4, UJ-1, FR-13
"Genuinely ambiguous" and "flagged/ambiguous rows" are used as if defined, but nothing states what makes a cell ambiguous.
Fix: Define ambiguity operationally in FR-4 (e.g. ink coverage between the Present and Absent thresholds).

FR-10 "similarity indication" has no shape

FR-10, FR-14

strong

"Sheet identifier" undefined but used as the DB idempotency key

Shape fit

UJ-4 — the marker running the brief's exact commands — is the smartest journey in the document, since that persona actually assigns the grade. Rigor is calibrated to coursework stakes. No findings.

Adversarial review

review-adversarial.md

This PRD reads like it was written from the brief's idealized table, not from the five real photos: the samples show signatures straddling row boundaries, overlapping each other, spilling outside the table border, and marker/grader annotations crossing into the table — all of which break the PRD's "ink in cell = Present" model that carries the graded 60%. Meanwhile the two artifacts everything else depends on — the info.xml schema and the sheet identifier — are left as open questions, so a 10-person team cannot parallelize on day one. Buildable eventually, but the hard 20% of the problem is exactly where the PRD is vaguest. (3 critical, 5 high, 5 medium, 4 low.)

critical

Sheet identifier has no obtainable source — FR-6/7/8 keyed on a value nobody can produce

§3, FR-6
Dates on the real sheets are handwritten in three different formats; OCR is a Non-Goal; the actual samples are named 1.jpeg–5.jpeg, so filename-derived dates fail too. Persistence, idempotency, queries, and graphs all hang off a field with no obtainable value.
Fix: Decide now — a required session element in info.xml and/or an explicit CLI/UI-supplied date; restate FR-6's key.
critical

Signature bleed-over invalidates the per-cell detection model — and FR-2 makes it worse

FR-2, FR-3, FR-4
Visible in the actual samples: signatures sit on row boundaries, spill outside the table border, and overlap across rows. FR-4's "cell contains ink → Present" will double-count or misattribute; FR-2's margin-exclusion consequence would delete evidence of a real signature.
Fix: Add an ink-attribution policy (connected components assigned by centroid/majority area, dilated ROIs, table-adjacent ink treated as candidate signature) and soften FR-2's margin exclusion.
critical

info.xml schema undefined — the most load-bearing contract is an open question

OQ-1; blocks FR-1/5/6/7/9/10/12/15
Until someone invents this file, the DB schema, parser, CLI contract, mapping logic, and Web UI upload validation are all blocked: a 10-person team cannot split the work. The group must author the file anyway, so the PRD has no excuse not to define it.
Fix: Put a concrete normative sample info.xml in an appendix, pending module-leader override.
high

Reference Signatures are circular — investigate.py may verify a signature against itself

FR-9, FR-10, SM-4
The only signature source is the five sheets under investigation; ≤5 samples per student, some contaminated by bleed-over. SM-4's mismatch test set does not exist.
Fix: Mandate the protocol: references = crops from sheets 1–3, probes = sheets 4–5, mismatch set = other students' signatures; documented metric + threshold.
high

Student Index mismatch "resolved" by deferring to a file that doesn't exist

§3, OQ-4, FR-7
A grader runs the brief verbatim — python infovis.py 001 — against a DB keyed on 10009301; FR-7's specified behavior is to report "no data." The program looks broken during marking precisely because it followed the PRD.
Fix: Require both forms to resolve — 001 as the sheet's No ordinal / short alias mapped in info.xml, plus the 8-digit Student No.
high

FR-11 vs FR-13 / Streamlit execution-model conflict unaddressed

FR-11, FR-13, §4.6
cv2.imshow cannot run inside a Streamlit server thread; naive ports reprocess the sheet on every widget interaction, colliding with FR-6 idempotency; two display code paths will drift.
Fix: Engine yields labelled stage images via callback/generator; both frontends only render; forbid cv2.imshow inside the engine.
high

Web UI adds ~3 FRs of work that earns zero rubric marks

§4.6, SM-6
Nothing in the assessment table awards marks for a responsive browser UI. Realistic outcome: strongest members polish Streamlit while cell localization — the graded hard part — stays brittle.
Fix: Keep it, but sequence it: Web UI work starts only after SM-1–SM-4 pass on all five sheets; cap the scope; state it is a demo aid, not a grade lever.
high

SM-1's ground truth is assumed, but the samples make ground truth itself ambiguous

SM-1, §9
Boundary-straddling signatures require human adjudication; without a frozen answer key, "100% accuracy" is unmeasurable and "or every error explainable" makes SM-1 unfalsifiable.
Fix: Require a committed ground_truth.csv adjudicated before tuning; score Disputed rows separately.
medium

"Fresh setup" has no supporting requirement — the graded commands can die on import

SM-2, FR-15
If the engine transitively imports Streamlit, the marker's machine gets ModuleNotFoundError on the brief's exact command. Also .png vs .jpeg formats unstated.
Fix: Engine/CLI depend only on OpenCV/NumPy/Matplotlib/stdlib; web deps optional; pinned requirements; clean-venv smoke test.
medium

Two stacked look-alike tables + printed-template ink: localization hand-waved

FR-3, FR-4
Every sheet has two grids of near-identical width; FR-3 asserts the metadata row is skipped without a mechanism. White-out patches and a red grader mark defeat naive colour filtering.
Fix: Name the mechanism (select the 5-column grid; mask detected grid lines before ink measurement).
medium

UJ-1/FR-13 promise a "flagged" state the data model cannot represent

UJ-1, FR-13, §3
Attendance Record is binary Present|Absent; no FR defines the ambiguity criterion or the review action.
Fix: Add a third stored state + manual-override flow, or delete the flagging promise.
medium

FR-14's "identical in content" parity is untestable as written

FR-14, FR-15
Comparing a Matplotlib window to a browser render has no defined check.
Fix: Define parity at the data layer (same query results / figure object), not pixels.
medium

Visualization — one of the brief's two "key technologies" — left as "chart TBD"

FR-8, OQ-3
"Counts and/or trend, exact chart TBD" is not enough for anyone to build a grader-facing "suitable graph" claim.
Fix: Commit a default (per-session presence timeline + attendance-rate summary), let OQ-3 upgrade it.
low

Row-count generality vs "static known layout" tension

§4.1, §6.2, SM-C1
All five samples have 6 student rows, but the prototype must accept "different images."
Fix: Say explicitly: column layout fixed, row count dynamic.
low

Template typos forbid header-text reliance

FR-3
Printed headers read "Lecture's Name" and "Signatue" (sic) — OCR-matching header labels is a dead end.
Fix: Warn implementers off header-text OCR in FR-3.
low

Date-format normalization

§3 Metadata Row
Three date formats appear across five sheets; the DB key needs one canonical format.
Fix: ISO 8601 in the Sheet Identifier definition.
low

Working title still unconfirmed

§0/§1
A draft-status header plus unconfirmed title in a document 10 people build from invites version churn.
Fix: Confirm the title before circulation.

Brief-coverage audit

review-brief-coverage.md

The PRD covers every development-relevant requirement in the brief — nothing is missing or contradicted; 26 requirements fully covered, 4 partial, 0 missing (30 traced). The dominant risk is not a gap but an addition: the mobile Web UI has no basis in the brief and diverts a marks-free share of a 10-person effort, though FR-15 CLI parity soundly mitigates the marker-facing risk. No material misreadings of the brief were found.

high

Web UI is un-briefed scope

§4.6, FR-12–14, SM-6
The brief's 60% prototype marks reward image-processing technique, OOP, testing, and the three CLI programs — not a mobile web frontend. Largest effort-diversion risk; also adds an unconfirmed framework dependency.
Fix: Gate the Web UI behind a completed engine + CLI (SM-1/SM-2/SM-3 met) and ensure the CLI runs with zero web dependencies installed.
medium

Group-of-ten contribution constraint not operationalized

§0
The brief requires all 10 members to contribute to both image processing and visualization; the PRD only name-checks it.
Fix: Add a short work-decomposition constraint or explicitly defer it to epics/stories.
medium

Live progress display weakened to "display or save"

FR-11
The brief: "While the program is running you need to show the progress." A save-only implementation would satisfy the FR while failing the brief.
Fix: Make live on-screen display mandatory; saving intermediates is supplemental.
medium

Committed higher-grade component rests on an unresolved blocker

FR-9/FR-10, OQ-2
The collection method is an open question the PRD itself calls blocking, with no fallback.
Fix: Default: crop Reference Signatures from the five sample sheets; hand-collected samples as enrichment.
low

Packaging / fresh-setup run not an explicit requirement

SM-2
The prototype must run from an unzipped copy on the marker's machine; no FR covers a dependency manifest, setup docs, or DB bootstrap.
Fix: Add a consequence: runs from a fresh unzipped copy with one-step dependency install; Local DB auto-created.

Mechanical notes

  • Glossary case drift: §3 Student Record says "supplied in the info file" (lowercase) where the defined term is "Info File."
  • SM-2 validates-list gap: SM-2's text requires investigate.py to run but its validates list omits FR-10.
  • Pipeline stage-list drift: FR-2 defines four stages including deskew, but FR-11/FR-13 display lists omit noise reduction and deskew.
  • Naming drift: PRD references sample_signin-sheets/ where the brief names CGV Signing Sheets.zip — confirm the folder matches the zip's five sheets.
